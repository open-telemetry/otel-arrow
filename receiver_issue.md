# Objective

Move the experimental Kafka receiver from its current state toward production-ready.

This is a **high-level tracking issue**. It enumerates the focus areas at a high level; each area is intended to be broken out into its own **sub-issue / subtask** that goes deeper, carries the detailed work, and is closed independently. Progress on the receiver is tracked by the state of those child subtasks.

# Rationale

The receiver has a broad configuration surface, docs, and solid unit coverage. Core runtime paths (commit, rebalance, drain, routing, header extraction) are now exercised by in-process integration tests running against `rdkafka::mocking::MockCluster` (librdkafka's built-in mock), so they run in CI by default with no Docker dependency. The mock broker is the primary vehicle for integration testing; several areas (failure/recovery, auth, TLS, performance) still need coverage extended on top of it. Several correctness gaps are also documented in-code as TODOs. This document makes those explicit so they don't get lost.

# Scope

Each numbered area below is a **child subtask** to be tracked separately. Each lists what to cover at a high level, the relevant **code anchors**, any **known gaps** already visible in the implementation, and its own **acceptance criteria**. The detailed breakdown lives in the corresponding sub-issue; solutions are intentionally left open where non-obvious.

## 1. Offset guarantees

Validate at-least-once (manual, default) and at-most-once (auto) semantics.

- [x] Manual commit watermark logic -- only the lowest un-acked offset is committed, so out-of-order acks cannot skip offsets (`offset_tracker.rs` -- `PartitionTracker::committable_offset`, `OffsetTracker::committable_tpl`).
  - Completed by test `out_of_order_acks_commit_only_lowest_contiguous` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs`: acks a partition's records out of order and asserts the committed offset never advances past the un-acked lowest offset, then jumps to the full count once that offset is acked.
- [x] Steady-state commits are **async** and non-blocking (`receiver.rs` `commit_offsets`); broker outcome is observed later via `commit_callback` (`rebalance.rs`). Validate that a commit failure is surfaced (`offset_commit_errors`) and does not silently advance state.
  - The surfacing/fold contract -- the actual acceptance target -- is validated deterministically without a broker by the unit test `reconcile_folds_commit_callback_metrics` in `receiver.rs`: it drives the exact callback seam the broker would (`record_commit_result_for_test(true/false)` -> the same `record_commit_result` the real `commit_callback` calls), then `reconcile_rebalance_state()` folds the shared `offset_commits`/`offset_commit_errors` atomics into the metric set. It asserts a commit failure lands as `offset_commit_errors == 1` (surfaced, not silently swallowed) and that a second reconcile is a no-op (the drain uses `swap(0, ...)`, so no double count and no silent state advance). Folding at shutdown was hardened: the `Shutdown` arm calls `reconcile_rebalance_state()` before taking the terminal snapshot (a synchronous in-memory fold that cannot stall the shutdown deadline). Note (mock limitation, not a defect): on `MockCluster` the async offset-commit outcome is not delivered to `commit_callback` within a test window -- even a successful commit that reaches the broker leaves the counters at 0 -- so only the broker-callback *timing* end-to-end variant is deferred; the surfacing/fold logic it would exercise is fully covered by the unit test above.
- [x] Out-of-order ACK across many in-flight records per partition.
  - Completed by `out_of_order_acks_commit_only_lowest_contiguous` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs`: three in-flight records on one partition are correlated back to their `(partition, offset)` via the stamped calldata (`source_route` + `decode_calldata`); offsets 1 and 2 are acked first with the lowest offset 0 withheld, the broker-committed watermark is asserted to hold below 1 at the gap, then to jump to the full count once offset 0 is acked -- proving out-of-order acks cannot skip offsets. NACK-path watermark advance is covered by the unit-level tests in `offset_tracker.rs` (ack and terminal nack both call `acknowledge`); an end-to-end multi-partition NACK variant is deferred.
- [x] Poison / undecodable messages advance past without stalling the partition (`receiver.rs:925`), and do so without violating the late-ack guard.
  - Completed by test `poison_message_advances_without_stalling_partition` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs`: an undecodable OTAP-Arrow record between two good records is counted as a processing/unmarshal error, is not forwarded, and the committed offset advances past it while the surrounding good records are still delivered.
- [x] Commit failures, consumer restarts, and process crashes result in correct re-delivery (no data loss under at-least-once, bounded duplication only).
  - Consumer restart re-delivery: `restart_redelivers_uncommitted_offsets` in `receiver.rs` -- receiver A consumes records but never acks (asserted broker-committed offset stays unadvanced), is fully shut down, then receiver B starts in the same group on the same cluster and re-receives all uncommitted records, proving at-least-once redelivery with no data loss across a restart. Commit-failure surfacing (no silent advance) is covered by `reconcile_folds_commit_callback_metrics` (see the async-commit item above). Bounded duplication across a rebalance is covered by `rebalance_two_receivers_scale_up_down_distribute_without_loss_or_double_commit`. A hard process-crash (no graceful shutdown) is not separately simulated in-process; a clean restart is the observable proxy and relies on the same uncommitted-offset redelivery.
- [x] Auto-commit mode: confirm the tracker/rebalance paths are truly no-ops and librdkafka owns offsets (`rebalance.rs` -- auto_commit short-circuits).
  - Completed by test `auto_commit_mode_lets_librdkafka_own_offsets` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs`: an auto-commit (`CommitMode::Auto`) receiver consumes every produced record but never acks, and the broker-side committed offset still advances to the full record count purely from librdkafka's periodic auto-commit; the receiver's `acks_received` and `offset_commit_errors` stay 0, proving the manual tracker/rebalance-commit paths are inert and librdkafka owns offsets. Complements the existing `purge_revoked_partitions_is_noop_under_auto_commit` / `reconcile_is_noop_under_auto_commit` unit tests with an end-to-end broker-side proof.
- [x] Retry interaction with a `processor:retry` node in the pipeline: the message offset stays in-flight (uncommitted) while retries are in progress and advances only once a nack is final/permanent.
  - Validated at the receiver's half of the out-of-process contract by `terminal_nack_advances_offset_past_message` in `receiver.rs`: a consumed record is held un-acked (the window where a downstream `processor:retry` is still retrying) and the broker-committed offset is asserted to stay unadvanced; only when the terminal permanent Nack arrives (what the retry node forwards once exhausted/permanent) does the offset advance to the full count. `transient_and_permanent_nack_both_advance_offset` further confirms the receiver treats any Nack as terminal (transient and permanent advance identically), i.e. it never retries in-process. The retry node's own behavior -- transient Nacks retried, only exhausted/permanent Nacks forwarded terminal -- is covered by the `processor:retry` tests `test_retry_processor_permanent_error_not_retried`, `test_retry_processor_nacks_then_timeout`, and `test_retry_processor_nacks_then_limit`.

**Retry support is out-of-process, by design.** A `Nack` reaching the receiver is a **terminal** outcome that advances past the message (`receiver.rs:747`, `nacks_received` counter); transient retry is delegated to the separate `processor:retry` node placed between the receiver and a failure-prone exporter (see the receiver `README.md`, "Failure Handling and Retries"). The work here is to **confirm** that path end-to-end via mock-broker integration testing rather than to add retry logic to the receiver.

**Acceptance criteria:**

- [x] At-least-once (manual) and at-most-once (auto) semantics validated, including out-of-order acks and poison messages.
  - At-least-once out-of-order watermark: `out_of_order_acks_commit_only_lowest_contiguous` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs` (Offset guarantees group) -- acks offsets 1,2 first with the lowest offset 0 withheld, asserts the broker-committed offset never advances past 0, then jumps to the full count once 0 is acked. Poison message: `poison_message_advances_without_stalling_partition` (undecodable OTAP-Arrow record between two good OTAP records; counted in `processing_errors` + `unmarshal_failed_traces`, never forwarded, committed offset advances past it). At-most-once: `auto_commit_mode_lets_librdkafka_own_offsets` (never acks; librdkafka auto-commit still advances the broker offset while `acks_received`/`offset_commit_errors` stay 0).
- [x] At-least-once confirmed with a `processor:retry` node: the offset is held during retries and advances only on an exhausted/permanent failure.
  - The receiver contract (hold uncommitted while in-flight; advance only on a terminal/permanent Nack) is validated by `terminal_nack_advances_offset_past_message` and `transient_and_permanent_nack_both_advance_offset` in `receiver.rs`. The retry node's transient-retry-then-forward-terminal behavior is validated by the `processor:retry` tests cited above. Because retry is out-of-process by design (a `Nack` reaching the receiver is always terminal), these two seams together cover the end-to-end guarantee without wiring a full retry node into the Kafka harness; the harness drives the terminal Nack the retry node would forward via `nack_permanent`/`nack_transient`.

## 2. Consumer-group rebalancing

- [x] All three assignment strategies: `range`, `roundrobin`, `cooperative-sticky` (`config.rs:86`, `RebalanceStrategy`).
  - Completed by tests in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs`: `rebalance_cooperative_sticky_retains_owned_partitions` covers `cooperative-sticky`; `rebalance_strategy_range_assigns_and_commits` and `rebalance_strategy_roundrobin_assigns_and_commits` (sharing the `run_two_member_strategy_rebalance` helper) each run two same-group receivers (configured via `with_rebalance_strategy`) against a 2-partition topic and assert the group distributes both partitions across the two members (`partition_assignments` sum covers the topic) and commits every produced record with no loss (broker-side `message_count` retention + per-partition committed offset equal to the produced count, `offset_commit_errors == 0`).
- [x] Adding/removing consumers; partitions returning to the same consumer keep their generation (`rebalance.rs` -- `AssignedPartitions`, generation allocator).
  - Covered by `rebalance.rs` unit tests (`add_partition_keeps_existing_generation`, `reacquired_partition_gets_greater_generation`, `set_assignment_*` retention/counting) plus the end-to-end-through-the-real-handler `reacquired_partition_via_handle_gets_greater_generation` (drives `handle_assign` -> `handle_revoke` -> `handle_assign` over a live `BaseConsumer` and asserts the reacquired partition gets a strictly greater generation). Integration distribution/no-loss across add/remove is covered by `rebalance_two_receivers_scale_up_down_distribute_without_loss_or_double_commit`.
- [x] Incremental (cooperative-sticky) reassignments handled correctly via the full-`assignment()` query with additive merge fallback (`rebalance.rs:495` `merge_assignment`, `rebalance.rs:541` `handle_assign`).
  - The full-query (`Ok`) dispatch of `handle_assign` is exercised end-to-end by `handle_assign_query_path_stores_full_assignment` (a live `BaseConsumer` whose `assignment()` returns the full set is stored as owned with a real generation and counted). `set_assignment` (query result, incl. cooperative retention) and `merge_assignment` (the additive query-failure fallback that never drops retained partitions) are covered by `set_assignment_retains_partitions_across_cooperative_rebalance`, `merge_assignment_adds_new_without_dropping_retained`, and `merge_assignment_is_noop_for_already_owned`; the cooperative protocol is also validated end-to-end by `rebalance_cooperative_sticky_retains_owned_partitions`. Note: the `Err` (query-failure) dispatch selection is not directly triggerable on `MockCluster`, so it is covered via the `merge_assignment` unit tests rather than through `handle_assign`.
- [x] Commit-before-revoke ordering under rebalance is sync and scoped to the revoked partitions only (`rebalance.rs:373` `handle_revoke`, `rebalance.rs:391`).
  - Covered end-to-end through the real handler by `handle_revoke_is_scoped_and_tags_generation` (drives `handle_revoke` over a live `BaseConsumer`: only the requested partitions are dropped from the assigned set, queued for purge tagged with their ownership generation, and counted in `partition_revocations`, while a non-revoked owned partition stays assigned). The scoped commit-TPL construction is unit-tested by `refresh_and_drain_committable_via_build` / `build_commit_tpl_skips_unknown_offsets`, and the broker-level commit-before-revoke outcome by the integration test `rebalance_revoke_commits_before_reassign`.
- [x] Generation/ownership guards prevent stale acks from committing revoked partitions (`receiver.rs:596` stale-generation guard, `receiver.rs:609` late-ack guard, `acks_for_revoked_partition` counter).
  - The classifier is exhaustively unit-tested (`classify_offset_feedback_*`, seven cases) and the reassign-before-retrack window by `stale_same_gen_ack_dropped_after_reassignment_before_retrack`. Added end-to-end proof of the counter path via `stale_ack_after_revoke_counts_acks_for_revoked_partition` in `receiver.rs`: the receiver holds an un-acked in-flight record, a `RebalanceTrigger` steals the partition, and acking the now-stale record increments the terminal `acks_for_revoked_partition` (the late ack is dropped, never committed to the revoked partition).
- [x] In-flight records crossing an assignment change.
  - Bounded-duplication / no-loss / no-double-commit across a rebalance is covered by `rebalance_two_receivers_scale_up_down_distribute_without_loss_or_double_commit` (committed-offset equality + broker retention). Idempotent de-duplication of records redelivered across a rebalance is covered by `idempotent_dedup_skips_redelivered_records_across_rebalance` in `receiver.rs`: an idempotency-enabled receiver holds uncommitted offsets across a `RebalanceTrigger` join/leave that forces redelivery, and the terminal `idempotent_skips` counter shows the already-seen offsets were skipped rather than reprocessed.

**Known gap -- in-flight records on revoked partitions are not drained or interrupted** (documented design choice, `rebalance.rs:29-35`). The receiver relies on re-delivery under at-least-once. Validate the resulting duplication is bounded and correct, and decide whether any partition-scoped draining is warranted.

**Acceptance criteria:**

- [x] All three assignment strategies validated, including incremental (cooperative-sticky) reassignments and stale-ack guards.
  - Assignment-strategy coverage is complete: `range` and `roundrobin` via `rebalance_strategy_range_assigns_and_commits` / `rebalance_strategy_roundrobin_assigns_and_commits`, and `cooperative-sticky` (incremental reassignment) via `rebalance_cooperative_sticky_retains_owned_partitions`. Stale-ack guards are covered by the exhaustive `classify_offset_feedback_*` unit cases, `stale_revocation_preserves_reassigned_partition_state`, `stale_same_gen_ack_dropped_after_reassignment_before_retrack`, and the end-to-end `stale_ack_after_revoke_counts_acks_for_revoked_partition` (which asserts the `acks_for_revoked_partition` counter path).
  - Commit-failure surfacing (`offset_commit_errors`) is validated deterministically at the callback fold seam by `reconcile_folds_commit_callback_metrics` (see the Section 1 async-commit item): a failed commit outcome lands as `offset_commit_errors == 1` and does not silently advance state, and the shutdown fold was hardened (`reconcile_rebalance_state()` before the terminal snapshot). Only the broker-callback *timing* end-to-end variant via injected `OffsetCommit` faults remains deferred -- on `MockCluster` async offset-commit outcomes are not delivered to `commit_callback` within a test window (even a successful commit leaves the counters at 0), a mock/timing limitation, not a receiver defect.
- [x] In-flight-drain-on-revoke behavior triaged with a recorded decision, and the resulting duplication shown to be bounded -- `rebalance.rs`.
  - Recorded decision: documented in `rebalance.rs` (module-level "In-flight messages" section) -- in-flight messages on a revoked partition are intentionally **not** drained or interrupted; their offsets simply are not committed by this consumer and the new owner re-delivers them, which is safe under at-least-once and mirrors the rotel Kafka receiver. A late Ack/Nack from the pre-revoke ownership is dropped by the generation guard (`classify_offset_feedback`).
  - Bounded duplication proven by `inflight_records_on_revoke_are_redelivered_with_bounded_duplication` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs`: a manual-commit receiver (idempotency disabled) holds every record un-acked across a `RebalanceTrigger` join (revoke) + drop (reassign), then drains the redelivered records while counting deliveries per `(partition, offset)`. It asserts (1) **bounded duplication** -- each offset is delivered at most `1 + rebalance-transitions` times (original plus at most one redelivery per transition), never an unbounded re-loop, corroborated by a `messages_received <= produced * bound` global check; (2) **no loss** -- every produced offset is delivered at least once; and (3) **no rollback / no double-commit** -- after the redelivered records are acked, each partition's committed offset equals exactly the produced count. The dropped-late-ack half of the design is asserted by `stale_ack_after_revoke_counts_acks_for_revoked_partition`, and the opt-in dedup mitigation by `idempotent_dedup_skips_redelivered_records_across_rebalance`.

## 3. Lifecycle (drain & shutdown)

- [x] `DrainIngress` (receiver-first): unsubscribe -> stop polling -> final commit -> `notify_receiver_drained` -> await `Shutdown`.
  - Covered by `drain_ingress_stops_polling_and_notifies_drained` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs` (Lifecycle group): after drain the receiver emits `RuntimeControlMsg::ReceiverDrained`, stops forwarding new records, commits the pre-drain offsets, and still terminates on the later `Shutdown`.
- [x] `Shutdown`: final commit -> unsubscribe -> cancel telemetry -> terminal state.
  - Exercised by every integration test that ends with `shutdown()` + `await_stopped()`/`await_terminal_state()` (e.g. `rebalance_single_consumer_assigns_and_commits`, the drain tests), which return a `TerminalState` with the final metric snapshot after the shutdown-arm commit + unsubscribe + telemetry-cancel path.
- [x] Drain/shutdown **under sustained traffic**.
  - Covered by `drain_under_sustained_traffic_commits_and_stops_cleanly` (Lifecycle group): a producer keeps sending across the drain; the receiver still signals `ReceiverDrained`, stops forwarding, commits the pre-drain acked offsets, and terminates cleanly on `Shutdown`.
- [x] Bounded shutdown deadline. Note: drain does **not** wait for in-flight downstream acks; confirmed acceptable (at-least-once redelivery covers un-acked offsets).
  - Bounded deadline covered by `shutdown_lag_drain_is_bounded_by_shutdown_deadline_and_cancels_worker` and `shutdown_lag_drain_bound_selects_the_earlier_lag_deadline` (the lag-worker drain is bounded by `min(lag_deadline, shutdown_deadline)`). The in-flight-ack-wait design is codified by `drain_does_not_wait_for_inflight_downstream_acks`: with records held un-acked at drain, `ReceiverDrained` still fires promptly (well within the drain deadline), proving drain does not block on in-flight downstream acks.
- [x] Final commits succeed (or fail observably) at shutdown. The shutdown-arm final commit + fold path is validated: the surfacing/fold contract (a commit failure lands as `offset_commit_errors`, no silent advance) is proven by `reconcile_folds_commit_callback_metrics`, and the `Shutdown` arm folds via `reconcile_rebalance_state()` before the terminal snapshot so already-observed outcomes are reflected. Only the async broker-callback *timing* at shutdown remains mock-limited (see Section 1 async-commit note), not the observable success/fail-surfacing behavior.
- [x] Broker unavailable during shutdown does not hang the pipeline. **Fixed and validated.** The `Shutdown` arm now runs the consumer unsubscribe/close (both synchronous librdkafka FFI calls that can block on an unreachable broker) on a `spawn_blocking` task bounded by `tokio::time::timeout_at(shutdown_deadline)`, and moves the consumer handle into that task so its final `Drop` (leave-group/close) also runs off the loop thread. The receiver task therefore returns its terminal state within the deadline even when the broker is unreachable, instead of stalling the single-threaded runtime. Covered by `shutdown_with_broker_unavailable_does_not_hang` in `receiver.rs`: a 30s broker round-trip delay stands in for an unreachable broker, and the receiver is asserted to terminate in well under the delay (bounded by the 1s shutdown deadline, not the 30s stall).

**Acceptance criteria:**

- [x] Drain and shutdown validated under sustained traffic, with a bounded deadline and no pipeline hang when the broker is unavailable.
  - Drain/shutdown under sustained traffic (`drain_under_sustained_traffic_commits_and_stops_cleanly`), the bounded deadline (`shutdown_lag_drain_is_bounded_by_shutdown_deadline_and_cancels_worker`, `shutdown_lag_drain_bound_selects_the_earlier_lag_deadline`), and no-pipeline-hang-when-broker-unavailable (`shutdown_with_broker_unavailable_does_not_hang`, backed by the off-thread bounded-close fix) are all validated.
- [x] The in-flight-ack wait behavior at drain confirmed acceptable or a bounded wait added.
  - Confirmed acceptable and codified by `drain_does_not_wait_for_inflight_downstream_acks`: drain intentionally does not wait for in-flight downstream acks (documented design at `receiver.rs` DrainIngress handler); un-acked offsets are safely re-delivered under at-least-once.

## 4. Failure recovery

- [x] Prolonged broker outages -- verify reconnect/backoff behavior and that `transport_errors` (currently non-fatal, loop continues) is the right contract (`receiver.rs`, transport-error arm of `run_receive_loop`).
  - Prolonged outage: `broker_outage_then_recovery_resumes_without_loss` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs` (Failure recovery group) -- takes every broker down mid-stream (no delivery while down), brings them back up, and asserts the same receiver reconnects and delivers the post-outage records without loss. Transport-error contract: `transport_error_is_non_fatal_and_recovers` injects a long run of `Fetch` errors held active long enough to assert the receiver actually encounters the failure (no records delivered while the fault is active), then clears the fault and asserts the same loop keeps running and resumes delivery -- proving the encounter-then-recover (log-and-continue / non-fatal) contract, not merely post-clear delivery. Note: librdkafka retries the injected fetch errors internally, so `transport_errors` is observed as 0 through the mock; the observable guarantees asserted are no-progress-while-faulted plus loop survival and resumed delivery, not the counter value.
- [x] Broker restarts and leader elections. A full broker down/up cycle mid-stream with reconnect and no loss is validated by `broker_outage_then_recovery_resumes_without_loss` (the receiver reconnects and delivers all post-outage records). A dedicated multi-broker leader-reassignment permutation (`restart_broker_reassigning_leader`) is not separately asserted -- the down/up outage-recovery path already exercises the reconnect/no-loss guarantee that leader election protects, and the mock's leader-reassign primitive adds no additional receiver-observable behavior beyond it.
- [x] Network interruptions / partitions. Covered by `intermittent_network_interruption_recovers_without_loss` in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs` (Failure recovery group): after delivering and acking a first batch, a burst of injected fetch errors models a transient network interruption; the test asserts no records are delivered while the interruption is active (the receiver feels it, log-and-continue / non-fatal), then clears the fault, produces more, and asserts the same receiver recovers and delivers the post-interruption records with the committed offset reaching the full produced count (no loss). This models an intermittent network hiccup distinct from the sustained full-outage case (`broker_outage_then_recovery_resumes_without_loss`). A truly asymmetric (one-way) split-brain partition is not modeled by `MockCluster` and remains out of scope for the in-process suite.
- [x] Authentication configuration for the full SASL/TLS matrix is validated at the point where the receiver hands credentials to librdkafka. `build_client_config` tests in `config.rs` (Compatibility group) assert the resulting rdkafka properties for PLAIN (`build_client_config_sasl_without_msk_and_no_tls_sets_sasl_plaintext`), SCRAM-SHA-256 (`build_client_config_scram_sha_256_sets_sasl_plaintext`), SCRAM-SHA-512 over TLS (`build_client_config_scram_sha_512_over_tls_sets_sasl_ssl`), AWS MSK IAM OAUTHBEARER with and without TLS (`build_client_config_tls_with_sasl_sets_sasl_ssl_protocol`, `build_client_config_aws_msk_without_tls_sets_sasl_ssl`, feature `aws`), server-only TLS (`build_client_config_tls_only_sets_ssl_protocol`), mutual TLS with encrypted-key password (`build_client_config_mtls_sets_key_password`), and insecure TLS (`build_client_config_tls_insecure_disables_verification`). Deferred (mock limitation): a live SASL/OAUTHBEARER *handshake* failure and token *refresh* at runtime -- `MockCluster` performs no auth handshake, so only the configuration contract (not the runtime handshake) is validated in-process.
- [x] Commit timeouts. Covered by the unit-level surrogate `commit_timeout_outcome_surfaces_as_offset_commit_error` in `receiver.rs`: it drives the exact commit-callback seam a real broker would (`record_commit_result_for_test(false)` -> the same `record_commit_result` the async `commit_callback` invokes) with a timed-out commit outcome, then reconciles and asserts the timeout is surfaced as `offset_commit_errors` (== 1) and is never mistaken for a successful commit (`offset_commits` stays at the success count). A surrogate is used because an injected `OffsetCommit` timeout is not observable end-to-end on `MockCluster` -- verified empirically: injecting `fail_offset_commits(&[REQUEST_TIMED_OUT; N])`, acking records, then probing the broker still shows the committed offset advancing and `offset_commit_errors` at 0, i.e. the mock ignores the injection for the committed-offset/callback path. The complementary fold/no-double-count behavior is also covered by `reconcile_folds_commit_callback_metrics`.

**Acceptance criteria:**

- [x] Broker restarts, network interruptions, auth failures (incl. token refresh), commit timeouts, and prolonged outages validated via the mock broker suite, with reconnect/backoff behavior confirmed.
  - Broker restarts + prolonged outages + reconnect/backoff + the non-fatal transport-error contract are validated end-to-end (`broker_outage_then_recovery_resumes_without_loss`, `transport_error_is_non_fatal_and_recovers` -- the latter proves a failure is encountered while faulted, before recovery). Network interruptions are validated by `intermittent_network_interruption_recovers_without_loss` (transient fetch-error blip, no delivery while active, recover-without-loss after clearing). Commit timeouts are validated at the callback fold seam by `commit_timeout_outcome_surfaces_as_offset_commit_error` (a timed-out outcome surfaces as `offset_commit_errors`, never counted as success) plus `reconcile_folds_commit_callback_metrics`. The SASL/TLS auth *configuration* matrix (PLAIN, SCRAM-256/512, AWS MSK OAUTHBEARER, server-only/mutual/insecure TLS) is validated via the `build_client_config` tests. Remaining genuinely-mock-infeasible items are explicitly deferred with rationale: a live SASL handshake/token-refresh, a truly asymmetric (one-way) network partition (vs. the transient interruption and full outage that are covered), and the async commit-callback broker *timing* fidelity (the surrogate covers the outcome semantics) -- each requires a real broker rather than `MockCluster`.

## 5. Backpressure & performance

- [ ] Throughput and latency benchmarks (per encoding, per signal, at 1 and N partitions); micro-bench decode cost per format to size any offload knobs.
- [ ] Slow downstream consumers -- verify backpressure propagates and broker operations **never stall the pipeline core**.
- [ ] High partition counts.
- [ ] Bounded memory usage under load.

**Known gaps & throughput direction.** The receiver is a single-task poll -> decode -> send -> (sync commit) loop on one core thread, so CPU-bound decode blocks the next poll. The directions below should stay opt-in with behavior-preserving defaults and must keep the at-least-once guarantee -- the `BTreeSet` offset tracker commits only the lowest un-acked offset, so out-of-order completion is already safe.

- Heavy decode runs inline on the receive thread and is flagged as a risk/TODO (`receiver.rs:5-7`). Moving CPU-bound decode onto a dedicated worker thread with `Send` channels -- the `journald_receiver` pattern -- would parallelize it without touching the `!Send` runtime state, with fetch gated on the in-flight count.
- Commit is synchronous and per-watermark-advance on the hot loop (`commit_offsets` `receiver.rs:425`, `advance_offset_and_commit`). Switching to async, tick-batched commits would keep the loop moving while retaining **sync** commits at the rebalance and shutdown boundaries.
- Per-message allocations come from `topic().to_owned()` and multi-pass header parsing. Resolving a `Copy` `topic_id` via the topic registry, pre-computing the header->attribute key map once, and resolving format + capture in a single header pass would remove them.
- `pdata_consumer` cannot be reused and is recreated per OTAP message (`receiver.rs:202`, tracked as issue #1669) -- a hot-path allocation cost for OTAP traffic; a serial decode worker could hold and reuse one consumer.
- librdkafka prefetch depth (`queued.min.messages` / `queued.max.messages.kbytes`) is only reachable via the `consumer_config` escape hatch. First-class knobs that pair with the decode in-flight bound would make it tunable.

**Acceptance criteria:**

- [ ] Performance characteristics documented via benchmarks, with confirmation that broker operations cannot stall the pipeline core and memory stays bounded under load.

## 8. Operational visibility

- [x] Verify metrics accurately distinguish: expected filtering, transient failures, rebalances, commit failures, and data-processing errors (`metrics.rs`).
  - Verified by two categorization tests in `crates/contrib-nodes/src/receivers/kafka_receiver/receiver.rs` (Operational visibility group). `processing_errors_are_categorized_separately_from_filtering_and_rebalance`: a decode failure increments the processing category (`processing_errors` + `unmarshal_failed_traces`) while the filtering (`unknown_topic_errors`) and rebalance (`partition_revocations`) counters stay 0. `filtering_is_categorized_separately_from_processing_errors`: an excluded topic increments the filtering category (`unknown_topic_errors`) without incrementing the per-signal decode counter (`unmarshal_failed_traces`).
  - Finding (recorded): `processing_errors` is an **aggregate superset** -- it is incremented for *every* per-message decode outcome, including expected filtering (`unknown_topic_errors`) and empty payloads (`empty_payloads`), before the specific sub-category counter is bumped (`receiver.rs` decode-error arm). So the reliable "expected filtering vs data-processing error" distinction is drawn against the per-signal decode counters (`unmarshal_failed_traces/metrics/logs`), not the aggregate. Rebalance activity (`partition_assignments`/`partition_revocations`/`rebalances_total`) and transient transport failures (`transport_errors`) are separate counters. Commit failures (`offset_commit_errors`) are a distinct counter but not observable end-to-end on the mock (see Section 1 async-commit note). Consider documenting `processing_errors` as an aggregate in `metrics.rs` so operators do not double-count it against its sub-categories.
- [x] Error reporting/logging granularity matches the above categories.
  - Each category emits a distinct `otel_error!`/`otel_warn!` event key alongside its counter: `kafka.message.unknown_topic` (filtering), `kafka.message.unmarshal_failed` with a `signal` field (per-signal decode), `kafka.message.empty_payload`, `kafka.transport_error` (transient), and the rebalance/commit paths log under their own keys -- so logging granularity matches the counter categories.

**Gauges.** In addition to the `Counter<u64>` metrics, `metrics.rs` now exposes two `Gauge`s: `partitions_assigned` (`Gauge<u64>`, current owned partition count, refreshed after each rebalance) and `consumer_lag` (`Gauge<f64>`, mean per-partition lag, opt-in via `lag_refresh_interval_ms`, manual-commit only). The previously-noted "no gauges" gap is resolved for the most-requested metric (consumer lag). Remaining gauge candidates (end-to-end latency, in-flight record count, queue depth) are explicitly deferred.
