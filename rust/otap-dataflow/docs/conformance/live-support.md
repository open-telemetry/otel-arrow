# Live reconfiguration support

Each operation applies to a running engine. A rolling replacement of the affected
pipeline qualifies. In-place updates have a separate column. A scenario link
identifies the check to run against the candidate. Current main has a known
receiver-add restriction under [discussion][correction].

**No live reconfiguration fixture** means the suite has no automated
add, change, or remove scenario for that registered component. The linked
entry describes the test environment and expected observation. An **exception**
links to a reviewed decision with an operator procedure and reason. A
**manual** cell links the steps and expected result for a specific
environment. Controller extensions are validated at startup. Pipeline
extension operations cover adding, changing and removing a binding and
observing the effect at its consumer. For catalog fixtures, the scenario link
opens the configuration and probe that the runner uses. The command reports
add, change and remove separately for the candidate. Each link describes
available coverage. A dash in the in-place column means that this index has no
recorded in-place promise. The component catalog and its owners should be
consulted when introducing or finding such a promise.

### Testing azure_key_vault_sasl_auth extension

authenticated reads by the Kafka receiver before and after the binding

### Testing azure_key_vault_user_pass_auth extension

The same isolated Azure identity and Key Vault HTTPS services, plus an

akv_database_bindings.

service accepted in each generation and verify its behavior after
unbinding.

### Testing flat_file_sasl_auth extension

Bind the provider to a Kafka receiver, consume a marked record, then
change the secret file path and consume a second record. Verify the
broker observed each expected principal and check delivery after unbinding.

### Testing etw receiver

subscription, and verify only selected events arrive. Remove and verify

### Testing internal_telemetry receiver

This receiver uses the internal telemetry settings supplied by the system

Boot with an observability pipeline, generate known telemetry, request an
observability pipeline change and check the rejection and continued

### Testing oracle receiver

A local Oracle service with a read-only fixture account, Oracle client
libraries for the production driver, and a table with distinct watermark
keys and phase-specific rows.

Deliver rows from the first query, change to the second query with an
isolated checkpoint, and verify marked rows and watermark progress. Remove
the receiver and confirm polling stops.

### Testing postgresql receiver

Use the receiver's fixtures/tls PostgreSQL service, private CA, and seeded
receiver_events table. The existing loopback startup and cancellation

Bind the fixture reader, check an identified row and checkpoint, change

### Testing sql_server receiver

A SQL Server instance with seeded rows, trusted TLS and a read-only login,
or a TDS peer that handles production schema discovery, parameter binding

Verify an identified row and its checkpoint, reconfigure the source or

### Testing user_events receiver

## Manual verification for an untested operation

Start an engine with two regular pipelines. Use the component README to
configure any required broker, credentials, platform or listening address.
Use a uniquely identifiable input and a capture sink on each pipeline.
From the target pipeline's committed config, prepare three candidate files
named `add.json`, `change.json` and `remove.json`. Each file contains
`{"pipeline": ...}`. Keep the observer pipeline outside every candidate.

- For a receiver, add a second input wired to the capture sink. Send a record
  through it, change its source or listening address, then remove it. Verify
  the new source delivers and the removed source stops.
- For a processor, insert it between the input and sink. Exercise a record
  whose result distinguishes the chosen settings. Change one setting and
  observe the new result. Remove the processor and verify the original path.
- For an exporter, add a reachable second destination, change the destination
  or a verifiable output setting, then remove the exporter. Check the actual
  receiving sinks and the remaining original route after removal.

For each candidate, run the following with the engine's admin URL as `BASE`
and the group and pipeline names as `GROUP` and `PIPE`. Verify the terminal
rollout state, committed configuration and sample delivery before submitting
the next candidate. Send a distinct observer probe during each rollout and
record its generation before and after. Finally, submit a candidate with a
missing connection target and verify both pipelines still deliver with the
previous committed configuration. Record build features, platform, commands,
observed values and a reference before promoting a cell to manual coverage.

```sh
curl --fail-with-body -X PUT -H 'Content-Type: application/json' \
  --data-binary "@$CANDIDATE" \
  "$BASE/groups/$GROUP/pipelines/$PIPE?wait=true&timeout_secs=30"
curl --fail-with-body "$BASE/groups/$GROUP/pipelines/$PIPE"
```

remaining environments above. Extend a fixture when a new operating mode,
